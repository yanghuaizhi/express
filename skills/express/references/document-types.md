# 文档用途与信息组织

按读者本次要完成的任务选择内容。下表是检查信息是否足够的依据，不是必填目录；已有模板、用户指定结构和局部修改范围优先。混合用途可以分层，但不要把所有分支拼成一份大模板。

| 用途 | 读者需要得到什么 | 应讲清的必要关系 |
|---|---|---|
| 方案、决策建议 | 是否做、选什么、为什么 | 目标与现状的差距；建议及依据；真实可行方案的收益、代价和适用条件；什么仍待决定 |
| 需求、功能说明 | 做什么、行为如何、何时算符合要求 | 对象与参与方；入口、输入、主要流程、已知例外和结果；已确认规则与待澄清事项 |
| 操作指南 | 在自己的条件下怎样完成任务 | 适用条件与前置；实际入口；顺序动作；有依据的成功标志；影响执行的分支与恢复方法 |
| 进展、管理汇报 | 目标现在到哪一步，差距是否影响计划 | 可用结果及范围；业务目标差距；已核原因或待验证解释；实际下一步和依赖 |
| 解释、技术说明 | 对象是什么、为何如此、怎样关联 | 必要定义；职责和输入输出；机制及适用范围；能帮助理解的具体例子 |
| 对外说明、交接 | 接收者据此了解事实或开展合作 | 对方需要的背景、能力、入口、使用方法、限制及已确认责任；排除与用途无关的内部过程 |

## 方案与决策

先回应当前要判断的问题。比较采用同一组与决定有关的维度，说明差异与取舍。没有来源的收益、评分或成本不要补造；用户明确的目标不要改成预计收益。

区分“建议采用”“已决定采用”和“当前已实现”。已经确认的同范围决定直接沿用；只有影响方向、覆盖、职责或承诺的新增取舍才需要对齐。新建议说明解决什么问题、依赖什么证据，不替决策者拍板。

不要为了结构完整强造多个选项；“保持现状”只有在实际可行且有助判断时才纳入比较。

## 需求与功能

已有功能迭代，讲清改动位置与改前、改后行为。全新功能按入口、对象、流程、规则说明，不虚构“改前”。

检查从输入到结果的链路是否能接起来：谁发起、谁处理、向谁返回什么；空数据、失败、撤回或返回编辑等分支，只写本次材料和行为确实涉及的部分。不要自创按钮、兜底、准入条件或其他模块职责。

把需求拆成便于理解与独立讨论的功能，但保留跨功能依赖。关键动作不要用“等”“相关处理”“按需优化”代替。若验收所需的结果状态未定义，明确缺口，不编造阈值。

## 操作指南

条件先于依赖它的动作。多个条件说明是全部满足、至少一个满足，还是互斥分支。使用真实的界面标签、命令和字段；无法核实的位置不要写成确定入口。

步骤按执行顺序排列，每步围绕一个主要动作。紧随动作的结果可写在同一步。独立动作分开；必须同步执行的动作不要拆成错误的先后顺序。

已有材料给出了成功标志或失败处理时，放在对应步骤附近。没有给出时，先核实或说明缺口，不默认重试、不擅加次数，也不把任何工具返回成功当作业务成功。

## 进展与汇报

先说明读者关心的目标状态及影响，再给依据。区分产物完成、功能测试、目标环境可用、规模可用和业务效果，不把完成了一份报告写成已带来增长。

数字写明相关的计数对象、范围和时段；分母不能只取成功进入后续流程的子集。下一步对应实际差距，已有责任人、依赖或期限应保留；没有时不强行分配。无需处置时，不编造待办。

## 解释与对外说明

从读者熟悉的对象解释陌生对象，再讲关系和机制。一个贯穿的例子通常比一串抽象名词更容易理解；例子涉及假设数值时就地标明。

检查接收者是否能脱离私人会话使用文档。必要前提与限制保留，无关内部争论和取证过程移出正文；是否披露来源取决于可用性与授权，不能为了显得有依据泄露内部信息，也不能捏造公共来源。
